# Spec: React app with services outside the React tree

This document is a self-contained brief for building a **demo app** to be presented to a frontend team. Read it fully before writing code.

## 1. Purpose

The team uses React Context as its dependency-injection mechanism, so core business logic (auth, storage, API access, …) lives in providers and hooks and is tied to React's rendering lifecycle. A proposal argues for:

- **Framework-agnostic core services**: plain TypeScript, dependencies injected explicitly, public API = state + commands + lifecycle (`init` / `dispose`).
- **Explicit lifecycle and imperative composition**: services are created, initialized and torn down by plain functions (the *bootstrapping phase*), not by provider nesting.
- **Context + hooks as thin UI adapters**: React obtains a handle to a service, subscribes to its state (`useSyncExternalStore`), and exposes UI conveniences. Nothing more.

The demo app must make these three ideas **obvious when reading the code and visible when clicking through the app**. It is a teaching artifact, not a product.

### Guiding constraints

- **Readability over completeness.** Every file should be readable in under a minute. Services are ~20–60 lines. No clever abstractions, no generic DI container, no store library (no Zustand/Redux/etc.).
- **Low fidelity, but a recognizable layout.** A clean, simple UI that resembles Nabla (ambient AI medical scribe): master/detail encounters view + full-screen settings with tabs. Tailwind only; no component library.
- **No tests.** Do not add Vitest or any test setup.
- **No new runtime dependencies** unless strictly necessary. The scaffold already has React 19, TanStack Router (file-based), Tailwind v4.

## 2. Existing scaffold

- Vite + React 19 + TypeScript, TanStack Router with file-based routing (`src/routes/`, `routeTree.gen.ts` generated by the Vite plugin), Tailwind v4 (`src/styles.css`).
- `src/main.tsx` creates the router and renders it. `src/router.tsx` is an unused duplicate (`getRouter`) — remove it or consolidate into one place.
- Path alias `#/*` → `./src/*` (package.json `imports`).
- `README.md` is the scaffold's default — it will be **replaced** (see §9).
- Run with `npm run dev` (port 3000). `npm run build` must pass with no type errors.

## 3. Domain

A simplified Nabla clone. A clinician logs in, sees a list of **encounters** (patient visits) in a sidebar, opens one to see its **note**, and can **record** the encounter (fake: a timer and a fake transcript that grows over time). A **settings** page holds profile info and preferences.

All data is fake and in-memory. Seed ~6–8 encounters (patient name, date/time, reason for visit, status `draft | completed`, a short note body).

## 4. Services

Every service:

- is a **class** implementing a public **interface**, created through a **`create*` factory** (the factory is what the rest of the code imports and calls):
  ```ts
  export interface AuthService extends Disposable { /* state, commands */ }
  class Auth implements AuthService { constructor(private readonly deps: AuthDependencies) {} /* … */ }
  export function createAuthService(deps: AuthDependencies): AuthService { return new Auth(deps); }
  ```
- declares its dependencies as an explicit `XxxDependencies` interface (empty / omitted if none).
- implements a shared `Disposable` interface: `dispose(): void | Promise<void>`.
- optionally has `init(): Promise<void>` when it needs async setup.
- if its state is reactive, exposes `subscribe(listener): () => void` and `getState(): XxxState`, where `getState` returns a **stable reference** until the state actually changes (required by `useSyncExternalStore`). A tiny shared helper (e.g. a `Store<T>` / `createStore` base with `getState` / `setState` / `subscribe`) is fine and encouraged to avoid repetition — keep it ~20 lines.
- logs its lifecycle through `logger` (created / init start / init done with duration / disposed).

### 4.1 App scope — created once in `bootstrapApp()`, before React renders

| Service | Depends on | Responsibility / what it demonstrates |
|---|---|---|
| `logger` | — | Console logger. Colored, scope-prefixed lines, e.g. `[app] storage ✓ init (412ms)`, `[session] apiClient ✗ disposed`, `[feature] recordingSession created`. Supports a child logger per scope (`logger.scope('session')`). The simplest possible service. Not reactive. |
| `storage` | `logger` | Key/value persistence over `localStorage` with an async `init()` (fake ~400–800 ms delay) that loads persisted data into memory. Gives the initial spinner something to wait for. |
| `notifier` | — | Toast notifications. Reactive (`subscribe` / `getState` → list of toasts). `notify({ kind, message })`, auto-dismiss after a few seconds. Callable from non-React code (other services use it). |
| `auth` | `storage`, `logger` | Fake auth. State: `{ status: 'signedOut' } \| { status: 'signedIn', user }`. `init()` restores the user from `storage` (so a page reload keeps you logged in). `login(email)` (fake latency, any email works, derive a display name), `logout()`. Reactive. |
| `session` | `auth`, app services, `logger` | **The session manager** — see §5.2. Owns the auth-session scope lifecycle. Reactive. |

### 4.2 Auth-session scope — created by `bootstrapSession(app, user)` on login, disposed on logout

| Service | Depends on | Responsibility / what it demonstrates |
|---|---|---|
| `apiClient` | `auth` user/token, `logger` | Fake in-memory backend with latency (~200–500 ms per call). Holds the seed data. Exists only while signed in. Every request is logged. After `dispose()`, any call throws ("apiClient disposed") — this makes teardown tangible. |
| `userSettings` | `apiClient`, `storage` | `init()` fetches settings (fake latency). State: e.g. `{ noteLanguage: 'en' \| 'fr', noteTemplate: 'soap' \| 'narrative' }`. `update(patch)` saves via `apiClient` and notifies. Reactive. Drives the Preferences tab. |
| `encounters` | `apiClient`, `notifier`, `logger` | List + get-by-id for encounters; reactive list state. Also **owns the feature scope**: `startRecording(encounterId)` creates a `recordingSession`, `stopRecording()` disposes it. On its own `dispose()` it disposes any active `recordingSession` (cascading teardown on logout). |

### 4.3 Feature scope — one per recording

| Service | Depends on | Responsibility / what it demonstrates |
|---|---|---|
| `recordingSession` | `encounters` (or the encounter id + an `onComplete` callback), `notifier`, `logger` | Created when the user clicks **Record** on an encounter. State: `{ status: 'recording' \| 'stopped', elapsedMs, transcript: string[] }`, updated by a `setInterval` (timer + a fake transcript line every ~2 s). `stop()` finalizes (e.g. notifies "Recording saved"). `dispose()` clears the interval. Disposed when the user navigates away from the encounter **or** logs out. |

Deliberately out of scope: i18n, gatekeeper/feature flags, encryption, FHIR/EHR, real auth.

## 5. Bootstrapping phase

"Bootstrapping" is the name for the imperative composition of services. Dependencies are wired **by hand**, in plain functions, in a readable top-to-bottom order. This is the centerpiece of the demo — make these files exemplary.

### 5.1 `bootstrapApp(): Promise<AppServices>`

```ts
export interface AppServices extends Disposable {
  logger: Logger
  storage: StorageService
  notifier: NotifierService
  auth: AuthService
  session: SessionManager
}

export async function bootstrapApp(): Promise<AppServices> {
  const logger = createLogger()
  const notifier = createNotifier()
  const storage = createStorageService({ logger })
  await storage.init()

  const auth = createAuthService({ storage, logger })
  await auth.init()

  const session = createSessionManager({ app: { logger, storage, notifier, auth } })
  await session.init() // if auth restored a user, bootstraps the session scope right away

  return { logger, storage, notifier, auth, session, dispose: /* reverse order */ }
}
```

- `main.tsx` calls `bootstrapApp()` **before** rendering the router. While it is pending, render a full-screen **app spinner**; on success render the router with services provided via Context (and also passed into the TanStack Router `context` so `beforeLoad` can read `auth`); on failure render the **error screen** (§6) whose Retry re-runs `bootstrapApp()`.
- Use a `Promise.all` where dependencies allow (e.g. independent inits) to show deliberate concurrency, but keep the order easy to follow.
- Teardown disposes in **reverse creation order**. A small helper (e.g. a `DisposableStack`-like `createScope()` that records disposables and disposes them in reverse) is welcome if it keeps bootstrap code shorter and clearer.

### 5.2 Session manager and `bootstrapSession(app, user): Promise<SessionServices>`

- `SessionManager` is an **app-scoped service**, created in `bootstrapApp`. It subscribes to `auth`:
  - on `signedIn` → state `initializing` → `await bootstrapSession(app, user)` → state `ready` with the session services.
  - on `signedOut` → dispose the current session services (reverse order, cascading into any `recordingSession`) → state `idle`.
  - on bootstrap failure → state `error` (with the error), plus `retry()`.
- State: `{ status: 'idle' } | { status: 'initializing' } | { status: 'ready', services: SessionServices } | { status: 'error', error: Error }`.
- Guard against races (e.g. logout while initializing → dispose what was created, don't end up `ready`). Keep it simple and commented.
- `bootstrapSession` mirrors `bootstrapApp`: `apiClient` → `userSettings` (await `init()`) + `encounters` → return `{ apiClient, userSettings, encounters, dispose }`.

The whole session lifecycle lives in plain TypeScript; React only reads `session.getState()`.

## 6. Failure demo

- A `?fail=<serviceName>` query param (read once by a tiny `demoFlags` module) makes that service's `init()` throw (after its normal fake delay). Must work at least for `storage`, `auth` (app scope) and `userSettings` (session scope).
- **One shared error screen** for both scopes: "Something went wrong", the error message, and a **Retry** button. App scope Retry → re-run `bootstrapApp()`; session scope Retry → `session.retry()`. Don't over-engineer this.
- Retry still fails while the query param is present — that's fine; the presenter removes the param to recover. (Optionally: only fail on the first attempt. Pick whichever keeps the code simplest and mention it in the README.)

## 7. React adapters

- One Context for app services (`AppServicesContext`) + `useAppServices()`. Session services are read from the session manager state (e.g. `useSessionServices()` that throws if not `ready` — only used under the authenticated layout).
- One small hook per reactive service, built on `useSyncExternalStore`, e.g.:
  ```ts
  export function useAuth() {
    const { auth } = useAppServices()
    const state = useSyncExternalStore(auth.subscribe, auth.getState)
    return { ...state, login: auth.login, logout: auth.logout }
  }
  ```
  Bind methods (arrow-function class fields or `.bind`) so they can be passed directly.
- `useRecordingSession()` / `useEncounters()` / `useUserSettings()` / `useNotifications()` / `useSessionState()` similarly.
- Hooks must stay tiny. **No business logic in hooks or components**, no `useEffect` for orchestration, except the one effect that disposes the recording when leaving the encounter route (or equivalently, an `onLeave` in the route definition — prefer the router hook if it reads well).

## 8. Routes & UI

File-based routes under `src/routes/`:

```
/login                         public. Email input + "Sign in" button (any email works). Redirects to /encounters if already signed in.
/                              redirect → /encounters (signed in) or /login (signed out)
/_authenticated                pathless layout. beforeLoad: redirect to /login if auth is signedOut.
                               Renders based on session state: initializing → spinner, error → error screen, ready → <Outlet/>.
  /encounters                  master/detail. Left: sidebar with encounter list (patient name, time, reason, status badge). Right: empty state "Select an encounter".
  /encounters/$encounterId     detail pane: patient header, reason, note body, Record / Stop button with elapsed timer and live fake transcript.
  /settings                    full-screen (no encounters sidebar), top tabs, back link to encounters. Redirects to /settings/profile.
    /settings/profile          read-only user info from auth (name, email) + "Log out" button.
    /settings/preferences      userSettings form (note language, note template). Saves via userSettings.update, toast on success.
```

Global UI:

- A slim top bar or left rail on authenticated pages: app name, link to settings, user avatar/initials.
- A toast area rendering `notifier` state (bottom-right).
- Full-screen spinner component reused for app bootstrap and session bootstrap (different label: "Starting app…" / "Loading your workspace…").
- Shared error screen component (§6).
- Keep the TanStack devtools in the root route if they don't get in the way; remove them otherwise.

Visual direction: calm, clinical, light theme; neutral grays with a single accent color; generous whitespace; readable typography. Low fidelity — no icons library needed, inline SVG or text is fine.

## 10. README.md (replace the scaffold README)

The README doubles as the presenter's script and a self-guided tour. Contents:

1. **One-paragraph intro**: what the demo shows and the three principles (framework-agnostic services, explicit bootstrapping, hooks as adapters).
2. **Running it**: `npm install`, `npm run dev`, open DevTools console to see the lifecycle log.
3. **Scope diagram** (ASCII or Mermaid): app scope → session scope → feature scope, with each service and its dependencies.
4. **Code tour — suggested reading order** with file links and a one-line "what to notice" per step: a service (`services/auth.ts`) → `bootstrap/bootstrapApp.ts` → `services/session.ts` + `bootstrap/bootstrapSession.ts` → `react/` adapters → `routes/_authenticated.tsx` → `services/encounters.ts` + `recordingSession.ts`.
5. **Demo scenarios** to click through, each with what to look at in the UI and in the console:
   - Cold start: app spinner while `storage` / `auth` init.
   - Login: session spinner while `bootstrapSession` runs.
   - Reload while signed in: session restored from storage.
   - Start a recording, then navigate to another encounter → recording disposed.
   - Start a recording, then log out from settings → cascading teardown (recording → session services in reverse order), `apiClient` disposed.
   - `?fail=storage` → app-level error screen + Retry.
   - `?fail=userSettings` → session-level error screen + Retry; app services still healthy (toasts, logout work).
6. **Rule of thumb** (short): keep visual/component-scoped concerns in React; extract a service when behavior must outlive a component, be shared outside a UI subtree, or be tested without React.

## 11. Acceptance criteria

- `npm run build` passes with no TypeScript errors; `npm run dev` works.
- Nothing under `src/services/` or `src/bootstrap/` imports React.
- All scenarios in §10.5 work as described, with clear console lifecycle logs (create / init / dispose per service, scope-prefixed).
- Disposal order on logout is visibly reverse of creation order in the console.
- No timers or subscriptions leak after logout (recording interval cleared, auth subscription of disposed services removed).
- Verify the scenarios in a real browser (the Playwright MCP tools are available for this) and check the console output.
